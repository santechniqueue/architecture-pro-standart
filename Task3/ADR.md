1. UI сайта и интернет-банка - React.js:<br>
Одинаковый фронтовый стек ускоряет delivery и унифицирует UX (U).<br>
Через Kong выполняем Strangler-Fig: часть роутов идёт в легаси-монолит, часть - в новые сервисы (S/R).
2. Каталог - Python + MS SQL мастер + KeyDB кэш:<br> 
MS SQL - единое хранилище ставок (S) и соответствует корпоративному стеку, KeyDB - быстрые чтения (U/P).<br>
Python хорош для MVP и легкого горизонтального масштабирования, есть сотрудники с опытом в Python разработке (кредитный скоринг).<br> 
Кэш прокрывает <200 мс p50 чтения на чтениях и SLA публикации ставок (U/P).
3. Интернет-банк - MVP на ASP.NET Core 8 + Kong + монолит на .NET 4.5:<br> 
MVP-сервис рядом с монолитом позволяет постепенно выносить функционал в новый стек, сохраняя совместимость (S) и снижая риски релизов, так как роуты можно откатывать на монолит(R).
4. Депозиты - ASP.NET Core 8 + PostgreSQL с Patroni и HA:<br>
Логика заявок и статусов отделена от каталога. PostgreSQL даёт транзакционность, а отказоустойчивость достигается за счёт Patroni (R).
5. Интеграции - Kafka + Python-consumer + Kong:<br>
Kafka как единая шина событий и отделение узлов от АБС (R), consumer - оркестрация и конверсия сообщений и вызовы в интеграционный прокси Kong (S).
6. АБС - ABS Adapter на ASP.NET Core 8 + PL/SQL:<br>
Anti-corruption layer изолирует схемы/процедуры АБС (S), место для идемпотентности и ретраев к процедурам, чтобы фронтовые сервисы были простыми и устойчивыми (R).

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
1. Оставить решение на монолите, расширяем текущий ASP.NET MVC 4.5 + ABS:<br>
Не вводить отдельные сервисы и доработать монолит интернет-банка и интеграции с ABS.<br>
Плюсы: минимальные интеграционные риски; быстрее старт, меньше DevOps-нагрузки; одна БД (MS SQL).<br>
Минусы: слабая масштабируемость, высокая связность; труднее обеспечить SLA/наблюдаемость; откат к единой точке отказа.<br>
Когда выбирать: очень жёсткие сроки и бюджет, низкая ожидаемая нагрузка, нет цели на последующую декомпозицию.
2. Полная переход на .NET Core 8 + MS SQL:<br>
Catalog, Deposits, ABS Adapter реализовать на ASP.NET Core 8 с единым MS SQL в качестве СУБД, KeyDB/Redis как кэш оставить.<br>
Плюсы: единый рантайм, язык и ORM; меньше операционной сложности; проще поддержка и онбординг; хорошая интеграция с существующим MSSQL-ландшафтом.<br>
Минусы: потеря гибкости стека; возможен технический долг, из-за сильной загрузки .NET-команды.<br>
Когда выбирать: сильная .NET-команда, требования к унификации платформы и снижению TCO.<br>
3. RabbitMQ вместо Kafka:<br>
Для команд и гарантированных доставок с низкой пропускной способностью - брокер сообщений (AMQP).<br>
Плюсы: проще операционно; удобен для RPC или команд; предсказуемые подтверждения.<br>
Минусы: хуже для стриминга и хранения истории событий; менее удобная реабилитация или повторы по истории.
Когда выбирать: поток событий невелик, нужен простой брокер.
4. Единый контур SMS через интеграции (без прямых вызовов из ABS):<br>
Оставить только IntegrationReverseProxy > SMSGateway, а ABS публикует событие.
Плюсы: единые шаблоны, аудит и идемпотентность; меньше дублей и коллизий.
Минусы: дополнительная задержка; зависимость от интеграционного контура SMS.
Когда выбирать: если есть запас на доработку в АБС.
5. Прямые вызовы АБС, без ABS Adapter:<br>
Сервисы ходят в процедуры АБС напрямую.<br>
Плюсы: быстрее старт MVP.
Минусы: хрупкость при изменениях АБС, сложность тестов и откатов; нарушение anti-corruption.
Когда выбирать: только как временный спайк с быстрым результатом.


**Недостатки, ограничения, риски**

1. Расщепление логики между монолитом и новыми сервисами:<br>
Риск: дублирование бизнес-правил, расхождение статусов.
Исправление: Strangler-план по маршрутам, единые доменные соглашения в ABS Adapter/Deposits.
2. Kong и Kafka как критические точки:<br>
Риск: misconfig, падение - деградация каналов.<br>
Исправление: HA, readiness/liveness; для Kafka - мониторинг лагов.
3. Среда интернет-банка и ABS слабо изолированы:<br>
Риск: нестабильные интеграционные тесты.<br>
Исправление: контракты (Pact/REST-контракты), sandbox-эмуляторы, фиксация тестовых данных.
4. Мульти-стек .NET/Python:<br>
Риск: «узкие места» на экспертизе, рост сложности поддержки.<br>
Исправление: команда под платформы.<br>
